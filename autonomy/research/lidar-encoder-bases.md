# LiDAR encoder bases: PointPillars → SWFormer

Research checked 2026-09-29. Read both full PDFs, including SWFormer’s appendix; inspected the PointPillars authors’ PFN/config and CenterPoint authors’ pillar/head code. Recommendations below are proposed SUREAL experiments, not published results.

## What transfers, and what changes

**PointPillars** discretizes only XY; Z remains a point feature. Original point decoration is `[x,y,z,r, x−mean_x,y−mean_y,z−mean_z, x−pillar_center_x,y−pillar_center_y]`. One linear/BatchNorm/ReLU layer produces 64 channels; max pooling over **points** produces one pillar token, scattered to dense BEV. A multiscale 2D CNN feeds an SSD-style anchor head: focal classification, SmoothL1 box residuals, direction classification, and NMS. Its defaults are 0.16 m XY, 12,000 pillars and 100 points/pillar. Original results are **KITTI**, front-view filtered LiDAR, with separate car and pedestrian/cyclist networks; neither KITTI range/anchors nor the reported 62 Hz should be treated as Waymo defaults or performance guarantees. [Paper §§2–4](https://arxiv.org/pdf/1812.05784).

The authors’ code confirms point-axis max pooling (the PDF’s “channels” wording is misleading), masks padded inputs, and exposes multilayer PFNs although paper results used one. The shipped car config uses a slightly different cropped range from the prose. Copying numerical configs verbatim would therefore conflate an architecture reproduction with dataset adaptation. [PFN/scatter implementation](https://github.com/nutonomy/second.pytorch/blob/master/second/pytorch/models/pointpillars.py), [car config](https://github.com/nutonomy/second.pytorch/blob/master/second/configs/pointpillars/car/xyres_16.proto).

**SWFormer** also uses **pillars** (“2D voxels”), dynamically voxelized at 0.32 m XY with unbounded Z; two 128-channel point MLPs embed them. Sparse window attention uses occupancy buckets, masked padding, post-norm, absolute sinusoidal position encoding and one half-window shift per block. Its five strides are `{1,2,4,16,32}`. Downsampling chooses the occupied token closest to the striding-cell center; upsampling copies coarse features only to occupied fine coordinates. Foreground segmentation precedes diffusion, inserting zero-initialized neighbor tokens before further attention and a modified CenterNet head. That head uses heading-bin, SmoothL1 and IoU losses; decoding uses local heatmap peaks without NMS. Waymo experiments use all five LiDARs and compare one/three frames. Appendix C adds a pointwise semantic head by concatenating pre-pooling point embeddings with fused pillar features; it reports preliminary joint-task mIoU 52.19 validation / 46.82 test. [Full paper §§3–4, Appendix C](https://arxiv.org/pdf/2210.07372).

Thus **PointPillars → SWFormer is a sensible pillar-encoder progression, but a full detector swap changes preprocessing, backbone, head and temporal input together**. SWFormer’s box-supervised foreground segmentation is separate from its appendix’s scene semantic segmentation. Adding semantics to PointPillars is our extension; using SWFormer’s appendix is an adaptation of a published preliminary extension. Neither paper establishes the proposed SUREAL self-supervised/pretraining objectives.

## Recommended sequence

1. **Waymo-adapted PointPillars, single frame.** Establish the shared point schema, coordinate system, point-to-pillar mapping, deterministic cap policy, train/validation split, boxes and point-label masks. Keep XYZ and the measured intensity/elongation separate from optional timestamp. Start with a modest dense BEV resolution/range selected for the local memory budget; log discarded points/pillars. Attach a per-point semantic head using point embeddings plus gathered BEV context. Compare detection-only, semantics-only and joint training before encoder changes. Call this an adapted baseline, not a reproduced KITTI result.
2. **Optional but valuable: CenterPoint-Pillar.** Keep the pillar encoder, CNN, points and schedule fixed and replace the anchor head with a center head. This isolates the head change and supplies a Waymo-tested bridge toward SWFormer’s center-based detector. Do not add two-stage refinement or multiple sweeps at this step. CenterPoint’s authors provide both pillar and voxel Waymo configurations; it is a head/framework choice, not intrinsically a new voxel representation. [Authors’ repo](https://github.com/tianweiy/CenterPoint), [Waymo configs/results](https://github.com/tianweiy/CenterPoint/blob/master/configs/waymo/README.md).
3. **SWFormer-style sparse pillar backbone, single frame.** First hold point features, XY resolution, embedding width and center head constant to measure a backbone change. Start with one/two/three scales; add sparse multiscale fusion, one shift per block, then foreground-guided diffusion. A dense diagnostic center head is useful during bring-up, but label that hybrid separately from the fully sparse paper architecture. Only after this controlled comparison introduce the paper’s dynamic voxelization, two-layer embedding and exact sparse head recipe as a second configuration.
4. **Temporal and representation learning experiments.** Compare one versus three ego-motion-aligned causal frames with timestamp offsets, preserving the same supervision and evaluation. Add the SUREAL representation/pretraining objective after the supervised pipelines work; compare random initialization, frozen pretrained features, and finetuning under the same labeled-data fractions. Include a label-free pretraining-only data manifest to prevent split leakage.

## Minimal ablations and measurements

| Question | Controlled contrast |
|---|---|
| Does the detector head explain gains? | PointPillars anchor vs CenterPoint center, fixed backbone |
| Does sparse attention improve features? | CNN vs sparse attention, fixed input/PFN/head |
| Does hierarchy matter? | 1/2/3 scales, then 5 only if context gains justify cost |
| Does crossing window boundaries matter? | Shift off/on, otherwise identical |
| Does center coverage matter? | Diffusion size 1 (off) vs 3/5; record center-token coverage and active-token count |
| Is discretization the explanation? | 0.16 vs 0.32 m; cap policy fixed and truncation reported |
| Do tasks help one another? | Detection/semantics separately vs jointly, label masks identical |
| Is history or pretraining responsible? | 1 vs 3 frames; random vs pretrained, matched compute/data |

Report per-class Waymo L1/L2 AP/APH for detection and per-class IoU/mIoU on genuinely labeled points for semantics; stratify by distance, large vehicles and pillar occupancy. Treat cyclist evaluation as an additional required implementation choice: the original SWFormer tables focus on vehicles/pedestrians. Measure end-to-end batch-1 latency, peak memory, active tokens and truncation on the **same local hardware**, including partition/scatter/head costs. Do not compare the papers’ KITTI/GPU and Waymo/TPU-XLA timings as an encoder benchmark. The diffusion and scale tests are especially useful because they separately address missing object-center tokens and long-range context.

## Bridges and framework constraints

**CenterPoint is the preferred optional bridge.** Authors’ PyTorch code directly exposes a reusable pillar encoder and center head. Its rotation encoding and postprocessing are not SWFormer’s exact head: the inspected implementation decodes sine/cosine rotation and supports circle/rotated NMS. Reuse its ideas while recording those differences. [Pillar code](https://github.com/tianweiy/CenterPoint/blob/master/det3d/models/readers/pillar_encoder.py), [head code](https://github.com/tianweiy/CenterPoint/blob/master/det3d/models/bbox_heads/center_head.py).

**SECOND is optional only for a height-resolution question.** A 3D voxel/sparse-convolution baseline would test whether preserving vertical bins helps; it also introduces sparse-convolution dependencies and changes more than the planned pillar-attention comparison. The PointPillars reference repo’s name `second.pytorch` does not imply PointPillars itself uses 3D sparse convolutions. Its README explicitly says SparseConvNet is unnecessary for PointPillars computation, although that old codebase expects installation. [Authors’ README](https://github.com/nutonomy/second.pytorch).

**SST is an optional implementation reference, not a mandatory experiment.** Its single-stride sparse attention preserves fine resolution, while SWFormer introduces hierarchy and sparse diffusion. The authors’ released MMDetection3D-based code is useful for window partition/masking and a practical fallback if a faithful SWFormer implementation is too costly. Keep this separate from claiming SWFormer reproduction. [SST paper](https://openaccess.thecvf.com/content/CVPR2022/papers/Fan_Embracing_Single_Stride_3D_Object_Detector_With_Sparse_Transformer_CVPR_2022_paper.pdf), [authors’ code](https://github.com/tusen-ai/SST).

**Choose PyTorch first if minimizing implementation risk; JAX is feasible but is a port.** PointPillars and CenterPoint authors release PyTorch code; SST is also PyTorch/MMDetection3D-based. No author SWFormer source repository or checkpoint was verified in this bounded search; do not promise an official PyTorch/JAX implementation. SWFormer reports TPU training and XLA compilation, which does **not** establish its original frontend as JAX or TensorFlow. Its masked attention, gather/scatter and reductions can be implemented in either framework; in JAX, explicit occupancy buckets/capacity shapes need careful JIT design.

Keep the SUREAL model/train runtime TensorFlow-free by consuming the project’s converted point/label records. Audit reference **data conversion and evaluation** separately: a PyTorch model does not establish that the bundled Waymo pipeline has no TensorFlow dependencies. A TFRecord filename in the historical PointPillars proto is not evidence of a TensorFlow model dependency. The exact no-TensorFlow Waymo ingestion/official-metric route must be checked in the dataset adapter, rather than inferred from these model papers.
