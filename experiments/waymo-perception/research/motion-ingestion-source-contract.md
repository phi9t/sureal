## Splits, framing, and timeline

Official split proportions are 70% training, 15% validation, 15% test. Data is sharded TFRecord containing either Scenario protobufs or tensorized tf.Example protobufs. Use the **Scenario** form for native evaluation and extension linkage. Training/validation prediction windows have 10 history states, one current state, and 80 future states at 10 Hz (91 total); test hides future truth (11 states). Train `tracks_to_predict` is a suggestion, while challenge validation/test targets are required. [Official Motion specifications](https://www.waymo.jp/intl/es/open/data/motion/), [pinned Scenario definition](https://github.com/waymo-research/waymo-open-dataset/blob/99a4cb3ff07e2fe06c2ce73da001f850f628e45a/src/waymo_open_dataset/protos/scenario.proto).

Scenario shards contain successive framed records, each parsed as `Scenario`; extension tutorials read one extension Scenario record from an uncompressed TFRecord (`compression_type=''`). This is evidence for the tutorial framing, not proof that every bucket object has the same compression. TFRecord itself uses little-endian 64-bit length, masked CRC32C of length, payload, masked CRC32C of payload. CRC masking is `((crc >> 15) | (crc << 17)) + 0xa282ead8`, evaluated as an unsigned 32-bit value; checksum type is CRC32C, not IEEE CRC32. Outer file compression and inner LiDAR compression are separate layers. [Official extension loader](https://github.com/waymo-research/waymo-open-dataset/blob/99a4cb3ff07e2fe06c2ce73da001f850f628e45a/tutorial/tutorial_womd_lidar.ipynb), [TensorFlow TFRecord format](https://www.tensorflow.org/tutorials/load_data/tfrecord).

`Scenario.scenario_id` is the authoritative unique scenario key. `timestamps_seconds[i]`, track states, and dynamic-map states share the same time index; `current_time_index` separates history/current/future. `compressed_frame_laser_data[i]` and `frame_camera_tokens[i]` correspond to this same timestamp grid only up through current time. Their types carry no independent per-frame timestamp field: retain the base Scenario timeline and verify the indexed contract. The LiDAR utility calls its coverage 1.1 seconds, whereas docs say first 1 second; 10 history samples plus the current endpoint implies **11 samples indexed 0..10**, not future input. Verify actual frame counts rather than relying on rounded prose. [Scenario definition](https://github.com/waymo-research/waymo-open-dataset/blob/99a4cb3ff07e2fe06c2ce73da001f850f628e45a/src/waymo_open_dataset/protos/scenario.proto), [LiDAR utility](https://github.com/waymo-research/waymo-open-dataset/blob/99a4cb3ff07e2fe06c2ce73da001f850f628e45a/src/waymo_open_dataset/utils/womd_lidar_utils.py), [camera proto](https://github.com/waymo-research/waymo-open-dataset/blob/99a4cb3ff07e2fe06c2ce73da001f850f628e45a/src/waymo_open_dataset/protos/camera_tokens.proto).

Official tutorials find an extension by the base `scenario_id` filename and copy the extension fields into a base Scenario. The utilities only append fields, and do not check IDs, release compatibility, repeated merging, or temporal leakage. Therefore proposed ingestion must check source filename/manifest linkage, reject conflicting extension IDs when present, reject duplicate augmentation, verify base timeline/current index and sensor counts, and retain extension-file provenance. Do not require an extension-only proto to contain all base fields: the documented extension may populate only the sensor repeated fields. [LiDAR augmentation](https://github.com/waymo-research/waymo-open-dataset/blob/99a4cb3ff07e2fe06c2ce73da001f850f628e45a/src/waymo_open_dataset/utils/womd_lidar_utils.py), [camera augmentation](https://github.com/waymo-research/waymo-open-dataset/blob/99a4cb3ff07e2fe06c2ce73da001f850f628e45a/src/waymo_open_dataset/utils/womd_camera_utils.py), [camera tutorial](https://github.com/waymo-research/waymo-open-dataset/blob/99a4cb3ff07e2fe06c2ce73da001f850f628e45a/tutorial/tutorial_womd_camera.ipynb).

## Sensor content and TF-free parsing recommendation

LiDAR fields hold zlib-compressed serialized `DeltaEncodedData`, with mask, residuals, shape and per-channel quantization precision. The official decoder uses zlib, protobuf and NumPy; decoding includes residual cumulative sums, mask reconstruction, channel-first reshape/transposition and quantization rescaling. This module does not import TensorFlow. Point extraction in `womd_lidar_utils.py` does import TensorFlow and applies calibration, per-pixel TOP pose and frame pose; copying only decompression does not establish a correct point cloud coordinate transform. [Compressed LiDAR schema](https://github.com/waymo-research/waymo-open-dataset/blob/99a4cb3ff07e2fe06c2ce73da001f850f628e45a/src/waymo_open_dataset/protos/compressed_lidar.proto), [official delta decoder](https://github.com/waymo-research/waymo-open-dataset/blob/99a4cb3ff07e2fe06c2ce73da001f850f628e45a/src/waymo_open_dataset/utils/compression/delta_encoder.py), [point extraction](https://github.com/waymo-research/waymo-open-dataset/blob/99a4cb3ff07e2fe06c2ce73da001f850f628e45a/src/waymo_open_dataset/utils/womd_lidar_utils.py).

Camera data is discrete VQ-GAN codebook indices, **not RGB images**. The tutorial encodes each camera image with 256 indices; the utility indexes an 8192-by-32 NumPy codebook to produce token embeddings. Preserve camera name, token order, integer range and codebook hash. The eight Motion cameras and token representation must not be confused with Perception RGB or joined to Perception by nearby timestamps, coordinates, filenames, or track heuristics. [Camera tutorial](https://github.com/waymo-research/waymo-open-dataset/blob/99a4cb3ff07e2fe06c2ce73da001f850f628e45a/tutorial/tutorial_womd_camera.ipynb), [codebook utility](https://github.com/waymo-research/waymo-open-dataset/blob/99a4cb3ff07e2fe06c2ce73da001f850f628e45a/src/waymo_open_dataset/utils/womd_camera_utils.py), [official camera specification](https://www.waymo.jp/intl/es/open/data/motion/).

Recommended parser: generate C++/Python protobuf bindings from the exact pinned source tree with protoc, read bounded TFRecord frames with both CRC checks, and parse payload directly as Scenario. No `tf.data`, TensorFlow wheel, tf.Example conversion or tutorial import is needed. Match descriptors/compiler/runtime compatibility and hash the descriptor set and native source tree. Decode camera embeddings by the official NumPy index operation; reuse the TF-free delta decoder with regression fixtures; separately validate any NumPy/C++ replacement for TF-based LiDAR point geometry. Keep immutable full truth separate from a model-input projection containing only states/dynamic signals/sensors with `i <= current_time_index`. This is a proposed engineering strategy grounded in the schemas and framing above, not an executed implementation or leakage certification.

## Deterministic small inventory proposal

This is a plan; no actual object inventory or cohort was acquired.

1. Once authorized metadata access exists, list the release's actual Scenario and extension prefixes. Persist every selected object's bucket, full name, generation, size, CRC32C/MD5 if supplied, updated time, format/compression declaration and owning release. Sort bytewise by object name. Google object metadata provides these identity fields. [Objects resource](https://cloud.google.com/storage/docs/json_api/v1/objects).
2. Select one training and one validation Scenario shard by lowest bytewise object name under a fixed byte budget; if any is over budget, apply a predeclared deterministic size/name rule. Freeze the inventory before reading any model result. This is a small reproducible pilot, not a representative full-release estimate.
3. After separately authorized acquisition, enumerate all records with shard generation, record index, byte offset, record hash and scenario_id. Choose, for example, 16 train and 16 validation scenarios by ascending `SHA256("motion-v1.2.1-pilot-v1" || split || scenario_id)`, with explicit length-prefixed encoding. Record exclusion reasons for malformed timelines or missing sensors. Do not select based on future behavior or evaluator success.
4. Resolve each chosen scenario's exact extension object from the observed inventory and `{scenario_id}.tfrecord` rule. For a strict multimodal cohort, freeze the intersection with available extensions before model comparison and report missing-extension counts. Metadata alone cannot recover scenario IDs inside a sharded Scenario object; that stage necessarily follows acquisition/parsing. [Official linkage](https://github.com/waymo-research/waymo-open-dataset/blob/99a4cb3ff07e2fe06c2ce73da001f850f628e45a/tutorial/tutorial_womd_camera.ipynb).
5. Keep split membership unchanged, preserve all required validation targets and non-target scene agents needed by native overlap evaluation, and compare all model variants on identical frozen records. Source windows can overlap; official split membership should be retained instead of inventing a random record split. [Official window/split specifications](https://www.waymo.jp/intl/es/open/data/motion/), [native evaluation API](https://github.com/waymo-research/waymo-open-dataset/blob/99a4cb3ff07e2fe06c2ce73da001f850f628e45a/src/waymo_open_dataset/metrics/motion_metrics.h).
